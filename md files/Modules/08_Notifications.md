# Module: Notifications

## 1. Purpose

Keep every actor informed of state changes relevant to them, across in-app,
email, and (future) push/SMS channels.

## 2. Actors

All roles receive notifications; Super Admin additionally has a
support-oriented view across all notifications for investigation.

## 3. Event → notification map

| Event | Recipient(s) | Default channel |
|---|---|---|
| Invitation sent | Student | In-app + email |
| Invitation viewed | Sending institution officer | In-app |
| Negotiation requested | Sending institution officer | In-app + email |
| Institution responds to negotiation | Student | In-app + email |
| Offer accepted | Sending institution officer | In-app + email |
| Offer rejected | Sending institution officer | In-app |
| Invitation withdrawn | Student | In-app + email |
| Invitation expiring (48h warning) | Both parties | In-app + email |
| Invitation expired | Both parties | In-app |
| Document verification result | Student | In-app + email |
| Org verification approved/rejected | Institution primary contact | Email |
| Subscription quota nearing limit | Institution org-admin/officer | In-app + email |
| Consultant client's invitation status changed | Consultant (active clients only) | In-app |
| New profile matches (saved search) | Institution officer (opt-in) | Digest email |
| Profile completion reminder | Student (opt-in) | Digest email |

## 4. Delivery modes

- **Real-time**: transactional, high-relevance events (invitation sent,
  negotiation, accept/reject).
- **Digest**: low-urgency, aggregatable events (new matches, completion
  reminders) — default daily digest, user-configurable frequency in
  `Modules/12_Settings.md`.

## 5. Business rules

- No event in the "state change" category (rule #16,
  `Product/02_Business_Rules.md`) can be permanently suppressed by a user —
  only its *channel/timing* is configurable, never full silence, to protect
  against missed deadlines (e.g., expiry warnings).
- Notifications are generated by the domain event itself (e.g., invitation
  status change), not polled — ensures no event is missed even if a user is
  offline.

## 6. Permissions

Each user reads only their own notifications. Super Admin can view
notification delivery logs platform-wide for support/debugging (not the
content of private messages beyond what's needed to resolve a ticket).

## 7. Database tables

`notifications`, `notification_preferences`, `notification_delivery_log`.
See `Database/Tables.md`.

## 8. APIs

`GET /notifications`, `PUT /notifications/{id}/read`,
`PUT /notifications/preferences` — namespaced under each role's API surface;
shared contract shape.

## 9. Reports

Delivery success rate, open/click rate on email notifications (Super Admin
view, product analytics).

## 10. Edge cases

- User has no verified email or phone yet → in-app only, until verified
  (`Modules/01_Authentication.md`).
- Digest notification window overlaps with a real-time triggering event →
  real-time always fires immediately in addition to being included in the
  next digest summary (no dedup suppression of the real-time one).

## 11. Future scope

- Push notifications (mobile app).
- SMS for time-critical expiry warnings.
- In-app notification center with filtering/search.
